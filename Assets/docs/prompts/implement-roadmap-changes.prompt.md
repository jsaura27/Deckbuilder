# Prompt: Implement Roadmap & Requirements Improvements

## Purpose
Consume the outputs generated by `audit-roadmap.prompt.md` (both Markdown and optional JSON) and apply selected changes to `roadmap.md` / `roadmap.json` and `requirements.md` / `requirements.json` safely, ensuring ID integrity, avoiding duplication, and deferring CI automation tasks unless explicitly enabled.

## Inputs
Implicit required files:
- `Assets/docs/audit-report.md`
- `Assets/docs/audit-report.json` (if present)
- Existing `roadmap.md`, `roadmap.json`
- Existing `requirements.md`, `requirements.json`

Optional runtime variables:
- `${input:applyList}`: newline or comma separated identifiers indicating which items to apply. Accepts task IDs, GAP IDs (e.g., GAP-001), recommendation titles, or slugs.
- `${input:applyAll}`: boolean-like ("true"/"false"). If true, applies all HIGH & CRITICAL gap recommendations plus new tasks listed.
- `${input:enableCI}`: boolean-like. Default false; when true permits creation of CI-related tasks.
- `${input:dryRun}`: boolean-like. If true, produce a plan of changes in a new `implementation-dryrun.md` without modifying source files.

## Selection Logic
1. If `applyAll` is true: select all items with severity High or Critical plus all recommendations with priorityScore >= threshold (default 5) and all newTasks.
2. Else if `applyList` provided: parse tokens; match against new task IDs, gap IDs, recommendation titles (case-insensitive), or slugs; ignore unknown tokens (log them).
3. CI tasks (category: Testing, Tooling & Automation, CI/CD) are excluded unless `enableCI` is true.
4. Always skip items already implemented (detect via existing task IDs or presence of matching slug).

## Implementation Responsibilities
1. For each selected new task: verify phase header exists in `roadmap.md`; append markdown checklist `- [ ] <title>` under the correct phase if absent; ensure unique ID in `roadmap.json` and add structured record.
2. For gap remediation that requires task creation: synthesize a concise task title and description; assign next ID in earliest viable phase; mark status `pending`.
3. For recommendation-based tasks: add tags derived from category (e.g., `testing`, `monitoring`).
4. Update `requirements.md` only when adding new entities/systems or refining acceptance criteria; insert or update a `"Enhancements"` section with subsections per category.
5. Maintain an `"Implementation Log"` section appended to `audit-report.md` listing each applied change with timestamp.
6. If JSON versions (`roadmap.json`, `requirements.json`) absent, update markdown only and add a warning note in the implementation log.
7. Never delete or alter completed (`done`) tasks except to add a non-invasive comment referencing improvement (e.g., `(Note: additional telemetry planned)`).
8. Preserve ordering of existing tasks; append new tasks at end of their phase list.
9. Validate uniqueness of new IDs and slugs prior to write; collision -> increment a numeric suffix (e.g., `slug-2`).
10. If dryRun: perform all validation and produce `implementation-dryrun.md` detailing intended changes, counts, and any collisions resolved, then stop without modifying core docs.

## Safety & Consistency
- All writes must be atomic per file (prepare full updated content then write).
- Abort on write protection with clear error report.
- If parsing `audit-report.json` fails, fallback to parsing `audit-report.md` heuristically (look for sections by headers).
- Do not create more than 25 tasks in a single run; if over, queue remainder listed under `Deferred` in log.
- For each created task include creation date ISO8601 and reference to originating GAP or recommendation.

## Output Artifacts
- Updated `roadmap.md` / `roadmap.json` (unless dryRun).
- Updated `requirements.md` / `requirements.json` when needed.
- Updated `audit-report.md` with Implementation Log.
- `implementation-dryrun.md` only if dryRun enabled.
- New `implementation-summary.json` capturing results:
```
{
  "applied": {
    "newTasks": number,
    "updatedTasks": number,
    "requirementsSectionsAdded": number,
    "notesAdded": number
  },
  "deferred": {
    "taskCreations": number,
    "ciTasks": number
  },
  "skipped": {
    "duplicates": number,
    "unknownSelectors": string[]
  },
  "warnings": string[],
  "timestamp": string
}
```

## Edge Cases
- Missing phase header: create it with placeholder description.
- Phase naming mismatch ("Phase 1" vs "Phase1"): prefer existing format from majority of headers.
- Unknown status values for existing tasks: leave unchanged; log.
- If no items selected: create `implementation-summary.json` with zeros and message "No matching items".

## CI Deferral
CI/CD improvements (pipelines, automated test runners, build monitors) are excluded unless `${input:enableCI}` is true. When false, list them in `implementation-summary.json.deferred.ciTasks` count.

## Finish
Return concise summary line: `Implemented: new=<nNew> updated=<nUpdated> reqSections=<nReq> notes=<nNotes> deferred=<nDeferred> skipped=<nSkipped>`.

## Success Criteria
Successful run applies only intended changes, leaves existing completed tasks intact, logs all actions with timestamps, and produces consistent JSON & Markdown artifacts or a complete dry-run plan.
