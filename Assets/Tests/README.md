Principles and conventions

- Unit vs Integration
  - Unit tests: fast, deterministic, run in the Editor test runner. Place under `Assets/Tests/Editor/<Area>/`.
  - Integration tests: longer, may touch disk or scene loading; place under `Assets/Tests/Integration/<Area>/`.

- Naming
  - Preferred: `<TypeName>Tests.cs` or `<Feature>NameTests.cs`.
  - When extending an existing test suite, use a suffix like `_Extended` (e.g., `CardDefinitionTests_Extended.cs`).

File placement rules (must-follow)
1. Do not place active tests directly under `Assets/Tests/` root. Root files are legacy and should be migrated.
2. Do not create test folders named after roadmap task ids (e.g., `Assets/Tests/2.3/`). Use descriptive area names instead (e.g., `Save/`).
3. Do not place tests directly under `Assets/Tests/Editor/` or `Assets/Tests/Integration/` (that is, no test .cs files should live at these directories' roots). All tests must be inside an area folder (for example `Assets/Tests/Editor/Save/` or `Assets/Tests/Integration/RunState/`).
  - If an appropriate area folder does not exist, create a new area folder under the correct parent (`Editor` or `Integration`) and place tests there.
4. Auto-generated or temporary scaffolding test folders are disallowed in the repository. If temporary scaffolding is needed for local experimentation, keep it out of commits; migrate any useful tests into canonical folders via a reviewed PR before merging.

- CI & test hygiene
  - Ensure test class names are unique across the codebase to avoid runner collisions.
  - Keep Editor tests small; tests that require heavy setup should be Integration tests.

Saving test agenda (task 4.3)

Purpose
  Provide focused, verifiable tests that validate the presence and basic shape of the Save System & Migration plan and the infrastructure needed to implement it. These tests are intended as CI smoke checks and as a developer aid while planning/implementing the save system.

Where to place tests
  - Editor unit tests: `Assets/Tests/Editor/Save/` (serialization, migration logic, smoke checks).
  - Integration / PlayMode tests: `Assets/Tests/Integration/Save/` (end-to-end save/load, backup/restore, file-system behavior).

Minimal checklist (recommended tests)

1) Save plan presence (Editor)
   - Assert `Assets/docs/plans/save-system-migration/plan.json` exists and contains the expected `task` string. Useful as a CI smoke test immediately after plan creation.

2) Save schema validation (Editor/CI)
   - If `Assets/docs/schemas/save.schema.json` exists, verify it is valid JSON and references expected subschemas such as `meta-progression.schema.json`.

3) Serialization round-trip (Editor)
   - A unit test serializes a `SaveData` POCO to JSON and deserializes it back, asserting that key fields remain equal.

4) Migration runner tests (Editor)
   - Unit tests that provide older-version payloads and assert migrations produce a current-version model.

5) End-to-end save/load (Integration)
   - Create a temporary save file, run SaveManager.Save, then SaveManager.Load and assert the resulting model matches expectations; test atomic write semantics (temp file -> move/replace) and backup behavior.

Quick implementation guidance

- For Editor tests that read workspace files (plan/schema), keep assertions lightweight and string-based to avoid introducing heavy dependencies.
- For serialization tests, prefer using the same serializer the SaveManager will use (Unity's `JsonUtility` or `Newtonsoft.Json`) and pin serializer settings in tests.
- When writing files in tests, use `Path.GetTempPath()` or `TestContext.CurrentContext.TestDirectory` to avoid modifying the repository workspace state.

Maintenance suggestions

- Periodically run a scan that enforces the placement rules and reports legacy root tests that should be migrated.
- If temporary scaffolding is created for rapid prototyping, do not commit it. Instead, keep it locally, and open a PR that migrates any useful tests into canonical folders after peer review.
