# Prompt: Implement Next Planned Task (Zero-Input)

## Overview
Automates implementation of the next task whose roadmap status is `planned`. It discovers the corresponding plan folder, validates its `plan.md` / `plan.json` pair, performs scoped edits, runs a build check, and updates status to `done` (or `error` if failure). No external input required.

## Implicit Inputs
- Roadmap file: `Assets/docs/roadmap.json`
- Requirements: `Assets/docs/requirements.md` / `requirements.json`
- Plan folders under: `Assets/docs/plans/`

## Task Selection Logic
1. Load `roadmap.json`.
2. Find first task with `status == "planned"` (fallback: first legacy task where `done == false` and `planFolder` exists).
3. If none found: abort with message "No planned tasks available".
4. Use `planFolder` path from roadmap task.

## Validation
- Ensure `planFolder` exists and contains `plan.md` & `plan.json`.
- Parse `plan.json`; compare task name/objective/deliverables with `plan.md`.
- If mismatch: set task status `error` with reason and abort.
	- Write minimal `changes-log.json` capturing failure reason.

## Scope Enforcement
- Only create/edit files explicitly listed in plan deliverables or implied required helpers.
- Helpers must be logged (filename + rationale) in `changes-log.json`.
- Never modify unrelated files or other plan folders.

## Implementation Steps
Iterate each entry in `plan.json.steps`:
1. Translate to concrete edits (file create/edit).
2. Keep edits atomic per file.
3. Use Unity conventions: `[Serializable]`, `MonoBehaviour`, `ScriptableObject`.
4. Place code in declared or standard paths:
	 - `Assets/Scripts/`
	 - `Assets/Editor/`
	 - `Assets/Resources/`

### Deliverable & Step Traceability
For every step, record at least one concrete artifact (created file path or edited file + line-range summary) in `changes-log.json.decisions[]` ensuring no step is left without a tangible outcome or explicit rationale for deferral.

### Minimal Test Generation & Execution
After implementing all steps (before final build status decision):

1. For every newly created non-abstract C# class under deliverables:
	- If `MonoBehaviour`: generate a test script that creates a temporary `GameObject`, adds the component, and asserts the component reference not null.
	- If `ScriptableObject`: generate a test that calls `ScriptableObject.CreateInstance<ClassName>()` and asserts not null.
	- For plain data classes (POCO / `[Serializable]`): instantiate via `new` and assert default public property values are accessible.
2. For each public method returning a primitive, enum, or struct with no parameters (or only optional parameters): invoke once to ensure no exceptions.
3. Place tests according to their type into one of the canonical test folders (do NOT use an AutoGenerated folder):
	- Follow canonical Unity test folder placement rules as defined in Assets/Tests/README.md

4. If a class cannot be safely tested (e.g., depends on heavy scene context), add a decision entry with context and rationale; still create a stub test marking `[Ignore("Context-heavy; deferred")]` if a test framework is available.
5. Execute a compile/build pass; if Unity's test runner integration is not accessible, treat successful compilation as proxy test execution; set `tests.executed=true` and summarize attempted classes and any skipped ones.
6. Populate `changes-log.json.tests` with:
	- executed (bool)
	- summary (string: count created tests, skipped tests, invocation counts)
	- failures (array: each with class, testName, message) – empty if compile-only.

### Completeness Verification (Pre-Finalization)
After test generation and build:
1. Re-scan deliverables from `plan.json.deliverables` and assert each path exists.
2. If any missing deliverable:
	- Attempt creation if trivial (e.g., specified as a config or script stub) and safe.
	- If still missing, mark task `status="error"` and list all missing paths in `changes-log.json.error` plus a structured `decisions[]` entry per missing item.
3. Ensure every step has either an implemented artifact or a deferral decision (UNFULFILLED_STEP).
4. Validate that no helper file resides outside allowed directories.

### Helper Files Policy
Helpers (supporting scripts, small utilities) may be added only if strictly necessary to satisfy a deliverable; each must have a `decisions[]` entry containing:
```
{
  "context": "Helper file creation",
  "decision": "Created Assets/Scripts/Helpers/<Name>.cs",
  "rationale": "Required for <deliverable X> to function; not listed originally"
}
```
Helpers are NOT appended to the plan; they are logged for transparency. Avoid broad frameworks.

### Post-Implementation Checklist
All of the following must be true for success:
1. `planFilesValidated == true` and `planMatch == true`.
2. All deliverables exist and zero UNFULFILLED_STEP decisions without error status.
3. `buildStatus == "success"` and no compile errors in created/edited files.
4. `tests.executed == true` and `tests.failures.length == 0`.
5. `summary.md` contains sections: `Overview`, `Implemented Steps`, `Deliverables`, `Test Execution`, `Verification`, `Next Considerations`.
6. Roadmap updated (`in-progress` -> `done`) with timestamps ordered: `startedAt < completedAt`.
If any checklist item fails, set roadmap task `status="error"` and include reason.

### Stricter Success Criteria
Success means not only build passes: every declared deliverable path must exist; each step is traced; tests executed; no silent omissions. Discrepancies produce error status—not partial completion.

## Build & Error Handling
1. After edits, perform compilation/build.
2. Collect errors for modified files; fix new ones introduced by this implementation.
3. If unrelated errors occur, revert affected new changes if feasible or mark task `error` with note.
4. Retry build up to 2 times after automated minimal fixes (e.g., missing `using` directives, obvious typos). Log each attempt outcome in `decisions[]`.

## Reporting Artifacts (written into plan folder)
- `changes-log.json`: includes
	- timestamp, task id, plan folder
	- filesCreated[], filesEdited[] (each with reason)
	- decisions[] (ambiguities resolved)
	- buildStatus (success|error)
	- error (if any)
- `summary.md`: high-level overview + verification steps.
	- Must include enumerated deliverables and explicit test execution summary.

## Changes-log format (strict)
The `changes-log.json` written into the plan folder MUST conform to the JSON Schema at `Assets/docs/schemas/changes-log.schema.json` (changes-log.schema.json). Implementations should validate the file against the schema before finishing.

Include a canonical `changes-log.json` template that follows the schema exactly (fill values as appropriate for the task):

```json
{
	"task": "<task-id-or-name>",
	"timestamp": "2025-11-01T12:00:00Z",
	"planFilesValidated": true,
	"planMatch": true,
	"filesCreated": [
		"Assets/Scripts/NewFeature.cs"
	],
	"filesEdited": [
		{
			"path": "Assets/Scripts/Existing.cs",
			"reason": "Add new method to support feature X"
		}
	],
	"decisions": [
		{
			"context": "Ambiguous requirement about input validation",
			"decision": "Implemented minimal validation to avoid scope creep",
			"rationale": "Requirement text was underspecified; this keeps behavior safe and local"
		}
	],
	"buildStatus": "success",
	"buildOutput": null,
	"tests": {
		"executed": true,
		"summary": "Created 5 test files, skipped 1 (scene-dependent). Invoked 8 parameterless methods.",
		"failures": []
	},
	"error": null
}
```

## Roadmap Status Transitions
Before starting implementation:
- Set `status = "in-progress"`, `startedAt = <ISO timestamp>`.

On success:
- Set `status = "done"`, `completedAt = <ISO timestamp>`, clear `error`.

On failure:
- Set `status = "error"`, record `error` message.

## Finish Output
Return a short confirmation containing:
- Task id & name
- Plan folder path
- Created/edited files counts
- Final status (done|error)

## Abort Conditions
- No planned tasks.
- Missing plan pair.
- Plan mismatch between human & machine versions.
- Deliverables target external/unowned paths.

## Unity Tips
- Keep generated data models partial or simple if future auto-generation planned.
- Wrap editor-only utilities in conditional compilation (UNITY_EDITOR).

## Non-Deviation Rules
- No schema modifications unless plan explicitly instructs.
- No broad refactors.
- All helper additions minimal and logged.
